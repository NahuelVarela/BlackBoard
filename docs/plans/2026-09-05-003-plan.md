### 0.1 Store fix (why separate table)

`store.rs::current` is `PRIMARY KEY(id)`. Problem #3 says `run-report.id`
matches the slice (e.g. `#3/dispatch`) — upserting it into `current` would
**replace the `slice-state` row and erase the tick**. So:

- `log.jsonl`: append everything (both types — append-only log unchanged).
- `current` table: only `slice-state` + `issue-opened` rows (as today). `upsert_if_newer` unchanged for these.
- New `reports` table: `CREATE TABLE IF NOT EXISTS reports(id TEXT PRIMARY KEY, actor TEXT, summary TEXT, ts TEXT, refs TEXT, extra TEXT)`; `append()` routes `type=="run-report"` there (upsert by id, latest wins by `(ts,actor)` same rule). Migration-safe: `CREATE TABLE IF NOT EXISTS`, no `ALTER` on `current`.
- New readers: `report_for(id) -> Option<Report>` / `all_reports() -> Vec<Report>` (indexer only). `all_current()` / `projection()` / tabs **unchanged** — `run-report` never enters ticks by construction (not just "ignored").
- `rebuild()` replays both tables from the log.

No `slice-state` envelope change, no reduction change, no writes from tabs/show.

**Slices are a mere list (for now).** Code must not hardcode slice names or
count. `bb sync` extracts `#N/<name>` IDs opaquely from the `## Slices`
section (table row or bullet-list line — both accepted); board/TUI render
whatever list comes back. The `#3/dispatch,blocked,tokens,tui,e2e` names below
are instances of #3's current list, not a schema.

## 1. Slice breakdown (instances of #3's current list, not a fixed schema)

### #3/dispatch — Dispatch verb + stream-json event loop
- `cli.rs`: `Dispatch { id: #N/slice, by, prompt?: Option<String>, resume?: Option<String>, mock_bin?: Option<String>, allow_tools?: Option<String> }`. Validate via `problem_of`+`slice_of` (both `Some`). Prompt default = `render_show(N)` context + agreement ("use AskUserQuestion when blocked, never assume; finish with 2-sentence summary").
- `dispatch.rs::run_dispatch`: assert `planning` then `executing` via `store.append` (reuse `default_refs`), spawn `claude -p <prompt> --output-format stream-json [--resume <id>] [--permission-prompt-tool "bb claude-hook ..."] [--allowedTools <allow_tools>]`, capture `session_id` from `system/init` message, `BufReader` stdout line-by-line → `claude.rs` parser until final `type:result` or EOF. `--mock_bin` overrides bin (e2e shim on `PATH`). Never pass `--dangerously-skip-permissions` by default. Loop attempts finish accounting (§tokens) before exiting; exit code propagates. Killing the loop kills/pauses the child.
- Tests: echo-shim spawn asserts planning→executing order, session_id captured, non-zero exit without result → `blocked` (not `done`).

### #3/blocked — AskUserQuestion → [!] + answer-back (CLI-only)
- Detection: `type:assistant` with `tool_use.name=="AskUserQuestion"` (plus `type:tool_use` variants with `--include-hook-events`). Extract `input.questions[]: [{question, header?, options:[{label, description?}], multiSelect?}]` + `tool_use_id`.
- On detection: (1) append `blocked` with summary `"<Q1 truncated 280ch> — unblocks on bb answer '#N/slice' --pick \"<label>\""` (v1 blocked rule); (2) write sidecar `.blackboard/pending/<N>-<slice>.json`; (3) pause tool call — answer returns via hook channel: `bb claude-hook` reads sidecar answer if present else "pending" keep-alive; JSON shape `{"permissionDecision":"allow","updatedInput":{"questions":…,"answers":{questionText:label}}}`. **Never re-prompt as a new user message** (e2e asserts mock got exactly one initial prompt).
- `bb answer {id, pick?, text?, all_json?}`: load sidecar (error if none: "no pending question for <id>"), match `--pick` against option labels (exact; error lists valid labels), write `{answers}` into sidecar, append `executing` ("answer supplied, resuming session <id>"); running loop re-spawns `claude --resume <session_id>` with answer for the hook. Single-question v1; multi via repeat or `--all-json '{"q":"label"}'`.
- Tests: sidecar round-trip, label-mismatch error, hook output contains `updatedInput.answers` mapping.

### #3/tokens — Finish accounting (type:result → run-report + done)
- `claude.rs::FinalResult`: tolerant serde — accept `total_cost_usd` OR `cost_usd` (prefer former), missing cache keys → 0, `usage{input_tokens, output_tokens, cache_read_input_tokens?, cache_creation_input_tokens?}`, `duration_ms, num_turns, is_error, model?`. Canonicalize to `RunReportExtra {session_id, cost_usd, input_tokens, output_tokens, cache_read, cache_write, duration_ms, num_turns, is_error, model}`.
- On final line: always write `run-report` (to `reports` table per §0.1, `summary="session <id> <ok|error>, <turns> turns, $<cost>"`). Then `is_error==false` → `done` via existing path, summary = first ~2 sentences of `result` (cap 280ch); `is_error==true` → `blocked` with `"run failed (<session>): <result truncated> — unblocks on re-dispatch / bb dispatch --resume <session>"`, no `done`.
- `tuple.rs` validation for `run-report`: require non-empty refs; skip open/done-summary rules; `extra` optional-but-expected.
- Tests: both cost-key spellings, missing cache, `is_error` true/false; `done` ≤2 sentences; error path asserts `blocked` not `done`.

### #3/tui — TUI + show read-side (pending question inline, cost line)
